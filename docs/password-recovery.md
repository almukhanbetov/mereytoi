# Восстановление пароля по резервному коду

MEREYTOI восстанавливает забытый пароль с помощью **одноразового резервного
кода**. Никаких SMS, WhatsApp или email: код получает сам пользователь и
хранит его у себя. Сценарий работает в приложении (Android/iOS) и на сайте
и не зависит от `PASSWORD_RESET_DELIVERY_ENABLED`.

## Для пользователя

### Как получить код

- **При регистрации.** Сразу после создания аккаунта приложение и сайт
  показывают код вида `ABCD-EFGH-JKMN-PQRS-TVWX-YZ01-2345` с кнопкой
  «Скопировать код». Сохраните его в надёжном месте: менеджер паролей,
  бумага в сейфе. Код показывается только один раз.
- **В настройках.** Приложение: «Профиль → Безопасность → Резервный код
  восстановления». Сайт: личный кабинет → «Аккаунт» → карточка «Резервный
  код восстановления». Там видно, создан ли код.
  - У аккаунтов, созданных до появления резервных кодов, кода нет. Экран
    пишет «Резервный код ещё не создан», а плитка в профиле — «Не создан».
    Введите текущий пароль и нажмите «Создать резервный код».
  - Если код уже есть, кнопка называется «Заменить код». Сначала
    появится подтверждение: старый код сразу перестанет работать.
  - Код показывается один раз. Посмотреть существующий код нельзя ни в
    приложении, ни через API — только создать новый.

### Как восстановить доступ

1. На экране входа нажмите «Забыли пароль?» (на сайте — страница `/recover`).
2. Введите email или телефон аккаунта, резервный код и новый пароль
   (не короче 8 символов). Регистр букв, пробелы и дефисы в коде не важны.
3. После успешной смены пароля вы сразу входите в аккаунт, а все остальные
   сессии на других устройствах завершаются.
4. Использованный код больше не действует: показывается **новый** код.
   Сохраните его.

Если ответ после смены пароля не дошёл (пропала сеть), пароль уже изменён.
Войдите с новым паролем и создайте новый код в настройках.

### Если утеряны и пароль, и код

Восстановить доступ самостоятельно нельзя: в этом весь смысл кода.
Напишите менеджеру MEREYTOI (WhatsApp или чат поддержки на сайте). См.
«Ручное восстановление» ниже.

## Безопасность

- **Код:** 28 символов из алфавита Crockford base32 (без I, L, O, U),
  140 бит энтропии, `crypto/rand`. Показывается группами по 4 символа.
- **Хранение:** в БД лежит только `sha256:` хеш кода
  (`users.recovery_code_hash`). Открытый код есть лишь в ответе на его
  создание. Такие ответы помечены `Cache-Control: no-store`. Код не
  пишется в логи, а приложения не сохраняют его на устройстве.
  Хеш без соли и без медленной KDF — сознательное решение: при 140 битах
  перебор по хешу невозможен, а быстрый хеш позволяет найти аккаунт по
  индексу.
- **Атомарность:** проверка кода, новый пароль (bcrypt), отметка
  `password_changed_at` и новый хеш кода записываются одним `UPDATE ... WHERE
  id = ? AND recovery_code_hash = <старый хеш>`. Из двух параллельных
  запросов с одним кодом успешен ровно один. Это проверено на Postgres
  тестом `TestInterleavedRecoveryRedeemsOnce`.
- **Сессии:** JWT, выданные до `password_changed_at`, отклоняются (секундная
  точность, как и при обычной смене пароля). Refresh-токенов в проекте нет.
- **Ограничение попыток** (таблица `recovery_attempts`, общая для всех
  экземпляров backend; ключи хранятся как SHA-256, без сырых IP и телефонов):
  - 5 попыток за 15 минут на аккаунт. Если email или телефон указывают
    ровно на один активный аккаунт, счётчик общий для этого аккаунта:
    попытки по email и по телефону складываются. Для неизвестных
    идентификаторов счётчик ведётся по самому идентификатору, и ответ
    при этом не меняется;
  - 20 попыток за 15 минут с одного IP;
  - 5 неверных текущих паролей за 15 минут при создании или замене кода.

  Счёт атомарный: попытка **сначала** записывается, потом считаются все
  записи окна, включая свою. Если их больше лимита — сразу 429. Поэтому
  при любом числе параллельных запросов проверку проходят не больше
  `лимита`. Отклонённые попытки тоже остаются в счётчике; успешная свою
  запись удаляет. Это проверено на Postgres тестом
  `TestConcurrentRateLimitPostgres` (25 и 30 одновременных запросов).
- **IP клиента** берётся Gin через `TRUSTED_PROXIES`, см. «Прокси и IP
  клиента» ниже. `X-Forwarded-For` и `X-Real-IP` учитываются только от
  доверенного адреса.
- **Пароли:** одна политика для любого **нового** пароля — регистрация,
  смена пароля, сброс через WhatsApp и восстановление по коду: не короче
  8 символов, не длиннее 72 байт (предел bcrypt). Старые пароли, заданные
  при прежнем правиле «от 6 символов», продолжают работать: правило
  проверяется только при создании пароля.
- **Логи:** SQL пишется без значений параметров, «record not found» не
  пишется (`internal/db/db.go`). Поэтому ни введённые логины, ни хеши кодов в
  лог не попадают. Восстановление пишет только `[recovery] … user #id`.
- **CSRF/CORS:** сессия передаётся заголовком `Authorization: Bearer`, cookie
  не используются, поэтому CSRF к этим endpoint'ам неприменим. Настройки CORS
  не менялись. Замена кода доступна только с действующей сессией
  (`RequireAuth` и проверка `password_changed_at`).
- **Одинаковый ответ:** неизвестный email/телефон, неверный код и
  неактивный аккаунт дают одно и то же: `400 {"error":"invalid_recovery_code"}`.
- **Телефон:** восстановление по коду не помечает телефон подтверждённым
  (`phone_verified_at` не меняется) и ни с чем по номеру не связывает аккаунт.
- **Ожидающие аккаунты** (созданные заявкой, `status=pending`) восстановить
  нельзя: они входят по ссылке-приглашению (AccountClaim).

## API

| Метод | Путь | Авторизация | Тело → ответ |
|---|---|---|---|
| POST | `/api/auth/register` | – | как раньше; в ответе также `recovery_code` |
| POST | `/api/auth/recovery/reset` | – | `{login, code, new_password}` → `{user, token, recovery_code}` |
| POST | `/api/users/me/recovery-code` | Bearer | `{current_password}` → `{recovery_code}` |
| GET | `/api/auth/me` | Bearer | также `has_recovery_code`, `recovery_code_created_at` (сам код — никогда) |

Ошибки: `invalid_recovery_code` (400), `weak_password` (400),
`password_too_long` (400), `wrong_current_password` (400),
`too_many_attempts` (429), `not_allowed` (403).

## Эксплуатация

### Миграция

Миграции выполняет GORM `AutoMigrate` при старте backend. Изменения только
добавляют данные, ничего не удаляют:

- `users.recovery_code_hash` (varchar(80), индекс) и
  `users.recovery_code_created_at` — новые nullable-столбцы;
- новая таблица `recovery_attempts`.

Отдельной команды нет: достаточно запустить новый образ backend.

### Прокси и IP клиента

Backend опубликован только на `127.0.0.1:8090`: снаружи к нему можно
попасть лишь через nginx на хосте. Gin доверяет заголовкам с адресом
клиента только от `TRUSTED_PROXIES`. По умолчанию это loopback и частные
сети, в том числе docker-шлюз, через который nginx попадает в контейнер.
`X-Forwarded-For` разбирается справа налево, и берётся первый недоверенный
адрес.

На VPS в `location /api` у nginx должно быть так (первая строка
перезаписывает то, что прислал клиент):

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Real-IP       $remote_addr;
```

Вариант `$proxy_add_x_forwarded_for` тоже безопасен: nginx дописывает
настоящий адрес справа, и Gin возьмёт именно его. Опасно, если nginx
передаёт клиентский `X-Forwarded-For` без изменений (`$http_x_forwarded_for`)
или не задаёт заголовки вовсе. Тогда клиент сможет выдать себя за любой IP.

Проверка снаружи, без изменения данных. При выключенной доставке
`password/forgot` ничего не пишет в БД, но имеет лимит 10 запросов с IP за
15 минут:

```bash
for i in $(seq 1 12); do
  curl -s -o /dev/null -w "%{http_code} " -X POST https://mereytoi.kz/api/auth/password/forgot \
    -H 'Content-Type: application/json' -H "X-Forwarded-For: 203.0.113.$i" -H "X-Real-IP: 203.0.113.$i" \
    -d '{"phone":"+77000000009"}'
done
```

Ожидается `200` десять раз и затем `429`. Если `429` нет, сервер верит
подделанному адресу, и nginx нужно поправить. На prod 3 ноября 2026 года
результат был `200 ×10, 429 ×2`: подделка не работает.

### Ручное восстановление (пароль и код утеряны)

Отдельного инструмента в админке пока нет. Менеджер должен убедиться, что
перед ним владелец аккаунта: совпадают имя, телефон и заявки, есть история
переписки. Затем администратор вручную задаёт временный пароль в БД
(bcrypt-хеш) и ставит `password_changed_at = now()`, чтобы завершить старые
сессии. Пользователь входит с временным паролем, меняет его и создаёт новый
резервный код. Не отправляйте временный пароль туда, где его могут увидеть
посторонние.
